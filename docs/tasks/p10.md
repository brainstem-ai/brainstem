# Task P10: Exact-answer cache and in-flight deduplication (rest of P10 deferred)

Repo: brainstem (bun + TS). Baseline: `ReflexEngine.request()` (the single shared call site for every reflex — gate/sanitize/verify/pulse/steer/select/focus all route through it), journal v2. All tests green.

**Scope note.** The plan's P10 bundles six sub-items of very different size and risk: (1) exact-answer cache + in-flight dedup, (2) optional journal seeding, (3) gate batching across independent pending actions, (4) post-result pulse/steer/select fusion, (5) a buffered journal sink, (6) optional gate prefetch. This unit is **(1) only**. The others need real harness restructuring (batching requires knowing when multiple pending tool calls are truly independent — today's harness handles one tool call at a time; fusion requires changing when reflexes fire relative to each other and to tool execution; prefetch requires hooking Pi's stream events) and deserve their own review, not a rushed pass here. (5) is explicitly conditional in the plan's own wording — *"if profiling justifies it"* — and no profiling has been done; disk I/O for small NDJSON appends is very unlikely to be the dominant cost next to network judgment round-trips, so building it without evidence would violate the plan's own stated condition. State all five deferrals plainly in the commit, not silently.

The cache is the right first piece: it's the most clearly and honestly measurable ("does the second identical judgment skip the network call entirely" is a yes/no fact, not a statistical claim), and it's additive — a correctness-neutral optimization that never changes what a decision *is*, only whether fetching its evidence required a new request.

## 1. packages/core/src/cache.ts (new)

```ts
export interface AnswerCacheEntry {
  answers: Record<string, Answer>;
  result: AskResult;          // the ORIGINAL call's result — model, latency, usage — for provenance
  originalJudgmentId: string;
  cachedAt: number;
}

export interface AnswerCache {
  get(key: string): AnswerCacheEntry | undefined;
  set(key: string, value: AnswerCacheEntry): void;
}

export function computeCacheKey(provider: string, state: unknown, questions: Record<string, Question>): string
export class BoundedAnswerCache implements AnswerCache { ... }
```

- `computeCacheKey` = `hashAction({ provider, state, questions })` — reuse the existing `hashAction`/canonical-JSON machinery from `evidence.ts`, same convention as every other content-addressed identity in this codebase (catalog hashes, section manifest hashes, action hashes). `provider` is the calling `SystemOne.name` (already includes the pinned model, e.g. `jev:jev-1.13.0` — see `jevSystemOne`), so a model change naturally produces a different key.
- `BoundedAnswerCache`: a `Map`-backed LRU (re-insert on `get` to refresh recency), bounded by both entry count (`maxEntries`, default 200) and estimated serialized bytes (`maxBytes`, default 2,000,000) — evict oldest-inserted first when either bound is exceeded. Evicting must decrement the tracked byte total correctly (test this explicitly — a leaked byte count that never shrinks is a real, easy-to-miss bug in this kind of structure).
- Cache **only** successful, fully-validated `"completed"` answers. Never cache `"unavailable"`, `"cancelled"`, partial/error group results, or anything from a static-floor path (those never reach `request()`'s success branch at all). This is the plan's *"do not cache permissions, approvals, cancellations, or failures"* — permissions/approvals aren't part of this cache's domain at all (they're tracked by `actionHash`, a completely separate mechanism this unit does not touch), so satisfying it here just means: only the success path populates the cache.

## 2. Wire into `ReflexEngine.request()` (packages/core/src/engine.ts)

Add `cache?: AnswerCache` to `ReflexEngineDeps`. Inside `request()`:

- Compute the cache key once, if a cache is configured, from `(this.systemOne.name, state, questions)`.
- **Check the cache before the budget check**, not after — a cache hit makes zero new provider calls, so it must never be blocked by a budget that exists specifically to bound *new* spend/time/calls. This is a deliberate ordering decision, not an oversight; say so in a comment.
- On a hit: **revalidate the cached answers against the current `questions`/`groups` on every use** (never trust that validity is preserved forever — a non-throwing revalidation wrapping the existing `validateAnswers`/`validateGroups` logic, since a schema mismatch on a hit should silently fall through to a fresh call, not surface as a new failure mode the cache itself introduced). On revalidation success: record the reflex event with `cacheHit: true` and `cachedFromJudgmentId: <original>`, return `{ status: "completed", result: <original AskResult, unchanged>, judgmentId: <this call's own new judgmentId>, answers: <revalidated> }`. The returned `result` carries the *original* call's latency/usage/model — that's the honest provenance; the journal event's `cacheHit` flag is what tells a reader "no new tokens were spent producing this."
- **In-flight deduplication**: a `Map<string, Promise<Judgment>>` of pending requests keyed the same way. Before issuing a fresh call (cache miss, or cache present but no configured cache at all), check for an in-flight promise for the same key; if present, await and return that instead of starting a second identical request. Register the new promise before awaiting the SDK call, remove it in a `finally` once settled (success or failure) — a failed in-flight request must not poison the map for the next distinct attempt.
- On a fresh, fully-successful (`"completed"`) non-cached result: store it in the cache, keyed the same way, before returning.
- Do not change budget/circuit-breaker/deadline behavior for the cache-miss path — this unit only adds a check before it and a write after it.

## 3. Journal (packages/core/src/journal.ts)

Extend the `"reflex"` event with two optional fields, and `recordReflex`'s signature to pass them through:

```ts
cacheHit?: boolean;
cachedFromJudgmentId?: string;
```

Absent entirely on a fresh (non-cached) reflex — don't emit `cacheHit: false` everywhere, that's noise; only write the fields when there's something to say.

## 5. Tests

`packages/core/test/cache.test.ts` (new):
- LRU eviction: fill past `maxEntries`, assert the oldest is gone and the byte total actually shrank (not just entry count) — construct entries with a known approximate size and assert the tracked total after eviction, not just "it didn't throw."
- Byte-bound eviction independent of entry count: one oversized entry alone should be able to trigger eviction of others even under `maxEntries`.
- `computeCacheKey` differs when provider, state, or questions differ; identical for identical inputs regardless of object key insertion order (reuses `hashAction`'s existing canonical-JSON guarantee — a one-line sanity test, not re-testing `hashAction` itself).

`packages/core/test/engine.test.ts` (extend):
- A cache hit skips `mockSystemOne` entirely (spy call count stays at 1 after two identical requests) and the second call's journaled reflex event carries `cacheHit: true` + the first call's `judgmentId`.
- Two DIFFERENT states/questions never collide (spy call count is 2 for 2 distinct requests).
- A cached entry that fails revalidation (simulate by mutating the cache's stored answers to something the current questions reject) falls through to a fresh call rather than surfacing a new error.
- `"unavailable"` and `"cancelled"` outcomes are never cached — a failing mock, retried after being reconfigured to succeed, must still make a real call (proves the failure never got stored).
- In-flight dedup: two concurrent (not sequential) `engine.gate(...)` calls with identical inputs, using a mock whose `ask()` doesn't resolve until manually released — assert the mock's `ask` was invoked exactly once, and both callers' promises resolve with equivalent decisions once released.
- Budget exhaustion (`maxModelCalls` already at limit) does not block a cache hit — only blocks a genuine miss.
