# Task P3: Approval lifecycle and stable task identity

Repo: brainstem (bun + TS). Baseline: journal v2 with IDs, SessionRecorder (packages/cli/src/session.ts), gate "ask" currently returns a blocked result telling the LLM to ask the user.

Goal: approval becomes a real harness lifecycle with an injectable callback, and task identity becomes explicit. TDD. Do not change decide* policy logic (P4/P5 own that).

## 1. new packages/core/src/approval.ts

```ts
export type ApprovalResolution = "approve_once" | "deny";

export interface ApprovalRequest {
  id: string;            // approvalId
  taskId: string;
  toolCallId: string;
  cwd: string;
  tool: string;
  validatedArgs: unknown;
  actionHash: string;    // hashAction from evidence.ts
  reasons: string[];
}

export type ApprovalHandler = (req: ApprovalRequest) => Promise<ApprovalResolution>;
```

## 2. harness.ts — gate "ask" flow

- HarnessOptions gains `approvalHandler?: ApprovalHandler`.
- Gate decision "ask": build ApprovalRequest, journal `approval` event (status "requested", using the v2 shape from journal.ts), then:
  - handler resolves "approve_once" → journal "approved" → return undefined (allow) — the exact validated action executes once this turn.
  - handler resolves "deny" → journal "denied" → return { block: true, reason: "[brainstem] denied by user" }.
  - handler throws or the caller signal aborts while waiting → journal "cancelled" → return { block: true, reason: "[brainstem] approval cancelled" }.
- Hard denials (static floor deny, gate deny) NEVER enter the approval flow.
- Approval binds to action inputs: hashAction(validatedArgs). If the file content for a pending write changed between request and resolution — you cannot detect this without revalidation; therefore re-check by re-hashing the args at resolution time inside the same hook invocation (args are fixed within one beforeToolCall call — document in one line that approval binds to the validated args of that hook invocation).
- Noninteractive runs (no handler): gate "ask" keeps today's behavior (blocked result instructing the agent to ask the user) but ALSO journals approval "requested" + "invalidated" with reason "no handler".

## 3. CLI approval handler (packages/cli/src/main.ts)

- REPL mode: implement an ApprovalHandler using the same readline input controller as task prompts. CRITICAL: approval responses must NOT become user task messages and vice versa — one input controller with two modes; while an approval is pending, stdin input resolves the approval (y/n), anything else is queued as a task update (print "queued until current action resolves" and deliver it as a steer AFTER resolution — use agent.steer with a user-role message for accepted task updates; do NOT lose input).
- Show the exact command/path, working directory, and reasons. Accept: y/yes/approve (approve_once). Anything else = deny. EOF = cancel (never approve).
- One-shot (--task) mode without TTY: no handler → noninteractive path above; if an approval is requested, exit with a distinct message "approval required" and CLI exit code 3.

## 4. Task identity (session.ts + harness.ts)

- `SessionRecorder.startTask(objective)` already exists. Add `updateTask(text)`: appends `task_update`, bumps revision, pushes to updates[]. PRESERVE the original objective — updates never overwrite it.
- harness.prompt(text): if the recorder has NO active task → startTask(text). If a task is active and the text looks like a constraint/update (heuristic: any text while a tool run is in flight OR explicit --update flag is out of scope — keep simple: a prompt while agent is NOT idle starts a new task; a prompt while idle starts a new task too; SO: task per prompt for now, BUT approval-time queued inputs delivered via agent.steer are task updates, recorded via updateTask, not new tasks). Document this one-paragraph rule in session.ts.

## 5. Tests (packages/cli/test/approval.test.ts)

- approve_once → the exact tool executes once in the run (spy execute count === 1), approval journal events requested+approved present.
- deny → execute count 0, blocked toolResult, approval requested+denied.
- handler throws → execute 0, approval cancelled, blocked toolResult.
- no handler (noninteractive) → blocked result + requested+invalidated events.
- floor deny bypasses approval entirely (no approval events).
- two sequential asks get two distinct approvalIds; one approval cannot satisfy the other (each beforeToolCall creates a fresh request).
- steered task update during approval does not replace the task objective (task_start objective unchanged in journal).
