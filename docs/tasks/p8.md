# Task P8: Skill loading, discovery, and dynamic context integration

Repo: brainstem (bun + TS). Baseline: `ReflexEngine.select`/`SelectDriver`/bitmap mechanics (P7), `CapabilityRegistry` (P6), richer reflex evidence (P5). All tests green.

Goal: make the registry's `active` bitmap actually govern what the agent can call, and let it load real skills. Today `CapabilityRegistry` is bookkeeping only — every baseline tool is registered with `impl: null`, and `harness.ts` builds its executable tool array by hardcoding `[...makeTools({cwd}), ...makeRecoveryTools({store})]` regardless of what the registry says. This unit closes that gap.

**Read `packages/cli/test/runtime-contract.test.ts` in full before writing any code.** It already pins the exact mechanism this unit must use — do not invent a different one:

- The provider-facing tool list is `agent.state.tools`, mutated directly. Tools travel out of band from `streamFn`'s `context.messages` — the test comment says so explicitly (`"tools travel out-of-band; they are not part of the streamFn context"`).
- Skill instructions are delivered as an **appended** `role: "system"` message pushed onto `agent.state.messages`, never by replacing the first system message that carries `DEFAULT_SYSTEM_PROMPT`.
- `Agent`'s `prepareNextTurnWithContext` hook (see `node_modules/@earendil-works/pi-agent-core/dist/types.d.ts`) is the integration point: it receives `{ message, toolResults, context, newMessages }` and can return `{ context: { messages, tools } }` to replace both for the next provider request. `AgentContext` only has `messages`/`tools` — there is no separate system-prompt slot in the returned context, which is why skill instructions go in as a message, not a prompt mutation.
- The existing first-turn test asserts the exact baseline name list `["bash", "glob", "grep", "read", "read_output", "search_output", "write"]` when nothing is explicit and no skill is registered. **This must not change** for a harness with no configured skills and no explicit selection — P8 is additive, not a behavior change for the zero-config case.

Do not build a provider context adapter, prefix/cache instrumentation, or checkpoint-boundary deferral in this unit — those need P11's checkpoint concept, which does not exist yet, and cache/prefix measurement, which has no instrumentation anywhere in this codebase to build on. Apply every tool-set/skill-instruction change at the very next turn boundary; that is the only timing spec this unit implements.

## 1. packages/cli/src/capabilities/skills.ts (new)

```ts
export interface LoadedSkill {
  descriptor: CapabilityDescriptor;   // kind: "skill", id: `skill:<name>`
  instructions: string;               // full SKILL.md body, verbatim
}

export function loadSkillsFromRoot(root: string): LoadedSkill[]
```

- A skill lives at `<root>/<name>/SKILL.md`. Parse YAML-ish frontmatter delimited by `---` lines at the top: `name`, `description`, `useWhen` (list), `avoidWhen` (list). Missing frontmatter fields default to `[]`/`""`; a missing `name` falls back to the directory name. Do not pull in a YAML library for this — the frontmatter shape here is small and flat; write a minimal line-based parser (`key: value` and `key:\n  - item` list forms only) and throw a clear error naming the file on anything else.
- `id = `skill:${name}`` where `name` is lowercased and has non-`[a-z0-9-]` characters replaced with `-`. Two files resolving to the same id is an error naming both paths.
- `contentHash = hashAction({ frontmatter, instructions })` (import `hashAction` from `@brainstem/core`) — a change to either invalidates the descriptor's identity, matching P6's `compileCatalog` convention that a changed body must not silently reuse an old catalog position.
- `alwaysAvailable: false` for every loaded skill — skills are optional by construction; only explicit selection or Select's judgment activates one.
- Validate paths: `root` and every skill directory must resolve under the configured project or an explicit skill-roots list (see §4) — reuse `packages/cli/src/paths.ts`'s `isInside`/`resolvePath`, the same containment convention P5 used for writes. Reject a skill root that resolves outside every configured allowed root.
- Loading instructions must not execute anything: no `require`, no shelling out, no following symlinks outside the validated root. Read the file with `readFileSync`, nothing else.

## 2. CapabilityRegistry additions (packages/cli/src/capabilities/registry.ts)

- `registerSkill(loaded: LoadedSkill): void` — calls the existing `register(loaded.descriptor, null)` (skills have no tool `impl`) and stores `loaded.instructions` in a new private `#skillInstructions: Map<string, string>`.
- `attachImpl(id: string, impl: unknown): void` — for capabilities registered with a `null` impl at construction time (today, every `BASELINE_TOOLS` entry): throws if `id` is unknown, throws if an impl is already attached and non-null (catches double-wiring bugs), otherwise sets it. This is how the harness later hands real `AgentTool` instances to `tool:bash`, `tool:read`, etc. after building them the same way it always has.
- `instructionsFor(id: string): string | undefined` — returns a skill's stored instructions, or `undefined` for a tool or unknown id.
- `pin(ids: string[]): void` / `unpin(ids: string[]): void` / `pinnedIds(): string[]` — a small explicit set the CLI layer manages (not `computeActive`'s business to invent; `computeActive` already accepts a `pinned` opt from the caller — this just gives something a place to keep that list across turns). Unknown ids in `pin` throw, matching `setExplicit`'s existing convention.
- `workingSet(opts, selected)` already takes `ComputeActiveOpts` (which includes `pinned`); pass `{ ...opts, pinned: [...(opts.pinned ?? []), ...this.pinnedIds()] }` internally so callers don't have to remember to merge pins themselves. Dedupe before passing to `computeActive`.

## 3. packages/cli/src/capabilities/discovery.ts (new) — `find_capabilities` tool

```ts
export interface DiscoveryDeps {
  registry: CapabilityRegistry;
  driver: SelectDriver;
  taskText: () => string;
  recentActivity: () => string[];
}
export function makeDiscoveryTool(deps: DiscoveryDeps): AgentTool
```

- Params: `{ query: string }`. Always available (`tool:find_capabilities`, `alwaysAvailable: true`, baseline — add it to `BASELINE_TOOL_IDS` and `BASELINE_TOOLS` in registry.ts alongside the existing five... six, after F0 added `read_output`/`search_output`).
- `execute` calls `deps.driver.refresh({ task: deps.taskText(), recent: deps.recentActivity(), discoveryQuery: params.query }, { reason: "discovery" })`. Discovery always runs — `SelectDriver.shouldRefresh` already special-cases `"discovery"` to bypass throttling (P7).
- On a decision with `status !== "unavailable"`: pin every recommended id that is not already baseline/explicit (`registry.pin([...newly recommended optional ids])`) and return a text summary: matched capability ids with their one-line descriptions, or an explicit `"no capability in the catalog matches '<query>'"` when `recommended` is empty — never a bare empty string.
- On `status === "unavailable"`: **do not fail the tool call.** Return a bounded deterministic candidate list instead — every eligible (non-baseline, non-explicit, available) capability in catalog order, capped at 20, each with id + description, prefixed with a line making clear this is unranked because the judgment was unavailable (`"Jev is unavailable; showing all eligible capabilities unranked — request one explicitly if it matches:"`). This is the plan's "a false negative does not trap the agent" requirement — a discovery outage must not leave the agent with zero path to a capability it needs.
- Discovery does not itself change `explicit` — it pins, which is weaker (released on task change, see §5) and separately tracked, so an agent-discovered capability doesn't get permanently conflated with a user's explicit request.

## 4. packages/cli/src/capabilities/context.ts (new)

```ts
export interface BuiltContext {
  tools: AgentTool[];
  activeIds: string[];
  instructionBlock: string | undefined;   // undefined when no active skill has instructions
  instructionHash: string | undefined;
}
export function buildActiveContext(registry: CapabilityRegistry, ws: WorkingSet): BuiltContext
```

- `activeIds = toIds(ws.active, registry.snapshotDescriptors())`, sorted (already sorted — `toIds` walks catalog order, which is already lexical by id per `compileCatalog`).
- `tools`: for each active id whose descriptor `kind === "tool"`, resolve `registry.impl(id)`; skip (with nothing thrown — log via a passed-in optional `onWarn?: (msg: string) => void`, default no-op) any active tool id with no attached impl rather than crashing the turn. This is a defensive floor, not an expected path — P8's own wiring (§6) always attaches every baseline tool's impl before the first turn.
- `instructionBlock`: for each active id whose descriptor `kind === "skill"`, look up `registry.instructionsFor(id)`. If none are active, return `undefined` (never inject an empty system message — matches F0/P5's "no unseen tail / no bare empty result" convention applied to skills). Otherwise join them, each skill's instructions preceded by a header line `## Skill: <id>`, sorted by id for determinism, and the whole block wrapped with a preamble: `"The following skill instructions supplement, and never override, the harness contract above."` — this sentence is the concrete implementation of "never let a skill override the harness's top-level contract."
- `instructionHash = hashAction(instructionBlock)` when defined, else `undefined` — used by the harness to detect "nothing actually changed" (§6) so an unrelated tool-set change doesn't re-inject an identical skill block as a new message every turn.

## 5. Trigger wiring (packages/cli/src/harness.ts)

- Construct one `CapabilityRegistry` (or accept `options.registry`, as today) and one `SelectDriver` (`packages/cli/src/capabilities/select-policy.ts`, P7) using `engine` and `registry`.
- Build the real tool array exactly as today (`[...makeTools({cwd}), ...makeRecoveryTools({store}), makeDiscoveryTool({...})]`), then call `registry.attachImpl(`tool:${t.name}`, t)` for every one of them, plus register any configured skills (`options.skillRoots?.forEach(root => loadSkillsFromRoot(root).forEach(s => registry.registerSkill(s)))`).
- **Initial turn:** before constructing the `Agent`, run one `SelectDriver.refresh({ task: <initial objective>, recent: [] }, { reason: "initial" })` synchronously awaited, then `buildActiveContext(registry, registry.workingSet(...))` for the `tools` passed into `Agent`'s `initialState`. When there is no configured skill root and no explicit selection, `recommended` is empty and `active` is exactly baseline — reproducing today's pinned test output byte-for-byte (BASELINE_TOOL_IDS grew by one item, `tool:find_capabilities`, in §3 — **update the pinned first-turn assertion in `runtime-contract.test.ts` to include `"find_capabilities"` in the sorted name list; this is the one intentional behavior change this unit makes, and it must be a deliberate one-line test edit, not a silent break**).
- **Every subsequent turn boundary:** implement `prepareNextTurnWithContext` on the `Agent`. On each call:
  1. Decide a `SelectTrigger`: `"task_update"` when the task's revision changed since the last refresh (harness already tracks `recorder.currentTask?.revision`), else skip calling `driver.refresh` entirely for this boundary (still proceed to apply whatever the last decision already produced, in case pins/registry changed without a fresh judgment) — do not call Jev on every single turn regardless of `minRefreshIntervalMs`; the trigger discipline in P7's `SelectDriver` is the throttle, but the harness must not manufacture a `"task_update"` trigger when nothing changed.
  2. Compute `ws = registry.workingSet({}, driver.currentDecision() && { evaluated: driver.currentDecision()!.evaluated, recommended: driver.currentDecision()!.recommended })`.
  3. `built = buildActiveContext(registry, ws)`.
  4. Compare `built.activeIds` (as a sorted, joined string) and `built.instructionHash` against what was actually applied last turn (track both in two closure variables, `appliedIdsKey`/`appliedInstructionHash`, initialized from the initial-turn setup in the previous bullet). If both are unchanged, return `undefined` — no context update this boundary.
  5. If either changed: journal a `capability_set` event (see §6) and return `{ context: { messages: built.instructionHash !== appliedInstructionHash && built.instructionBlock !== undefined ? [...context.messages, { role: "system", content: built.instructionBlock, timestamp: Date.now() }] : context.messages, tools: built.tools } }`. Update the two tracked variables.
- Tool-set shrinkage is immediate: if a previously active tool drops out of `active` (dependency broke, explicit selection changed, pin released), it is simply absent from `built.tools` starting the very next turn boundary — no special-casing needed since `prepareNextTurnWithContext` already fires once per turn boundary and this unit always applies the freshest `active` set there.
- Discovery-driven refresh (§3) happens inside a tool `execute`, mid-turn. It updates `driver`'s internal decision immediately, but the new tool set/instructions only reach the model at the *next* `prepareNextTurnWithContext` call (i.e., after the current assistant turn's remaining tool calls finish) — this is a direct, intended consequence of the single integration point above, not a gap to patch; note it in a comment so a future reader doesn't "fix" it into a second code path.
