## 1. packages/core/src/output-sections.ts (new)

```ts
export interface OutputSection {
  id: string;              // `${artifactId}:${index}`, index = position in source order
  artifactId: string;
  startByte: number;       // UTF-8 byte offset into the original content, inclusive
  endByte: number;         // exclusive
  text: string;            // exact verbatim source slice — never summarized or rewritten
  requires: string[];      // ids of sections this one depends on to interpret correctly (e.g. its header)
}

export interface SectionManifest {
  catalogHash: string;     // hashAction({ schema: SECT_NAMESPACE, artifactId, sections }) — import SECT_NAMESPACE from ./capabilities
  entries: readonly OutputSection[];   // stable, source order
}

export function splitIntoSections(artifactId: string, content: string): SectionManifest
export function dependencyClosure(manifest: SectionManifest, selectedIds: readonly string[]): string[]
```

`splitIntoSections` is one function handling one stream (stdout or stderr) of one artifact. A caller with both streams calls it twice with artifactId suffixes `:stdout`/`:stderr` — this module is stream-agnostic and knows nothing about tool semantics.

Splitting rules, in this order:

1. **Blank-line paragraphs.** If `content` contains at least one blank line (`/\n\s*\n/`), split on runs of blank lines. Each non-empty resulting block is a candidate section, in source order.
2. **Header/child grouping within a paragraph split.** If a block's first line matches a header pattern — `/:\s*$/` (ends with a colon), `/^(PASS|FAIL|ok|not ok)\b/i`, `/^\s*(test|it|describe)\(/i`, or a line of 3+ repeated `=`/`-` characters immediately followed by a non-blank line — treat that first line's block as a header section, and treat the immediately following block(s) that are indented (start with whitespace) or that directly abut it with no blank line as children whose `requires` includes the header's id. A header with no qualifying children is just an ordinary section with `requires: []`.
3. **Dense fallback.** If step 1 finds no blank lines at all (one dense block — a giant stack trace or unstructured log), split into fixed non-overlapping line windows of `LINE_WINDOW = 40` lines each, `requires: []` for all of them (no natural parent exists).

Byte offsets: compute via `Buffer.byteLength(prefix, "utf8")` on the UTF-8-encoded content preceding each section, never JS string `.length`/UTF-16 code units — this is the specific defect the plan flags in the completed pilot ("The pilot used UTF-16 string offsets; production must specify and test byte/line semantics, Unicode boundaries"). A section containing multi-byte UTF-8 characters (emoji, accented text, CJK) must have `endByte - startByte` different from the UTF-16 `.length` of the same text whenever such characters are present — a test must assert this directly, not just that offsets exist.

`dependencyClosure` transitively follows `requires` (BFS/DFS over `manifest.entries` keyed by id) starting from `selectedIds` and returns the union, deduplicated, in manifest order. This is simpler than `capabilities.ts`'s `computeActive` — no availability/rejection semantics, just closure. Do not reuse or extend `computeActive` for this; sections have no notion of "unavailable."

## 2. packages/core/src/output-focus.ts (new)

```ts
export type FocusMode = "full" | "select" | "compute_or_retrieve";

export type FocusSectionReason =
  | { kind: "selected"; score: number }
  | { kind: "dependency" }              // pulled in by dependencyClosure, not scored itself
  | { kind: "excluded"; score: number }
  | { kind: "over_budget"; score: number }
  | { kind: "unevaluated" };

export interface FocusInput {
  task: string;
  command: string;
  intent?: string;
  outcome: "ok" | "error" | "timeout" | "cancelled" | "blocked";   // reuse the ToolStatus vocabulary from evidence.ts, do not invent a new one
  recentFindings: string[];
  manifest: SectionManifest;
  budgetChars: number;
}

export interface FocusDecision {
  mode: FocusMode;
  status: "ok" | "partial" | "unavailable";
  sectionManifestHash: string;
  evaluated: CapabilityBitmap;     // reused bitmap type; catalogHash namespace makes it non-interchangeable with a capability bitmap
  selected: CapabilityBitmap;
  scores: Record<string, number>;
  reasons: string[];               // short human-readable summary lines, for logging/journaling
  sectionReasons: Record<string, FocusSectionReason>;   // full per-section audit trail
  batches: number;
}
```

- `const FOCUS_MIN_CHARS = 800;` `const FOCUS_BATCH_CHAR_BUDGET = 6_000;` (mirror P7's `SELECT_BATCH_CHAR_BUDGET` naming/value, but keep this a separate constant — do not import or share P7's).
- `isExhaustiveTask(input: Pick<FocusInput, "task" | "intent" | "manifest">): boolean` — **pure code, never a Jev call**, true when any of:
  - `input.task` or `input.intent` matches `/\ball\b|\bevery\b|\bexact(ly)?\b|\bcomplete list\b|\bfull output\b|\bhow many\b|\bcount\b/i`.
  - `input.manifest.entries.length <= 1`.
  - the manifest's total text length (`sum of entries[i].text.length`) is `<= FOCUS_MIN_CHARS`.
  A `true` result means the caller (F2) presents the full bounded view; this module still returns a well-formed `FocusDecision` with `mode: "full"`, empty `scores`/`sectionReasons` (nothing was evaluated — it never got that far), `evaluated`/`selected` as empty bitmaps over the manifest's catalogHash, `status: "ok"`, `batches: 0`. Do not call Jev in this path.
- `encodeSectionId(id: string): string` / `decodeSectionId(encoded: string): string` — mirror `selection.ts`'s `encodeSelectId`/`decodeSelectId` exactly (same `focus__` prefix convention instead of `select__`, same colon-escaping), so both modules stay independently auditable but consistent in style. Section ids already contain a colon (`artifactId:index`) — the escaping must round-trip that.
- `buildFocusQuestions(candidates: OutputSection[]): Record<string, Question>` — one required `noul` per candidate: `"Given task, the action command (intent: intent), outcome, and recentFindings, is this section necessary evidence for judging whether the action succeeded or for deciding the next step? Section: \`<text, capped at 2_000 chars per question — cap the text placed IN the question, never the stored section.text itself>\`."` Plus one **optional** noul per candidate, `contradicts_hypothesis` variant, id-suffixed `__contradicts`: `"...does this section contain evidence that contradicts the current hypothesis in recentFindings, or evidence that an already-attempted approach failed?"` — its answer, when present, can only *add* a section to `selected` (a high contradiction score selects a section even if its main relevance score was below threshold); it never removes one that already qualified on relevance.
- `batchSections(candidates: OutputSection[], budget = FOCUS_BATCH_CHAR_BUDGET): OutputSection[][]` — same greedy-by-serialized-size batching algorithm as P7's `batchCandidates`, duplicated here rather than imported (these two modules must stay independently combinable without cross-importing each other's internals — the plan's "distinct namespaces so they cannot be accidentally combined" principle extends to not sharing a batching helper that would otherwise become an implicit coupling point).
- `decideFocus(manifest, candidates, answers, policy, budgetChars): { selected: CapabilityBitmap; evaluated: CapabilityBitmap; scores; sectionReasons }` — pure function:
  1. For each candidate with a relevance answer: record score; `contradicts` answer (if present and `>= policy.focus.relevanceNoul`) can flip an otherwise-excluded section to selected with `sectionReasons[id] = { kind: "selected", score: <relevance score> }` — the contradiction check does not gain its own reason kind; it just changes the outcome of the existing relevance-based decision, so `reasons` stays traceable to one score field.
  2. Sort qualifying (>= `policy.focus.relevanceNoul`) candidates by descending score. Greedily accept into `selected`, running a byte-count budget that includes each accepted section's own `text.length` *plus* the sizes of any not-yet-selected dependencies its `requires` pulls in (compute via `dependencyClosure` per acceptance, checking incremental cost only for ids not already in the running selected set). The first candidate that would exceed `budgetChars` is marked `over_budget` (along with everything after it in the sorted order — do not keep scanning for a smaller one that might still fit; simplicity over marginal packing efficiency here) and the loop stops.
  3. Anything scored below threshold and not flipped by a contradiction answer → `excluded`.
  4. Anything in `candidates` with no answer at all in either question → `unevaluated`.
  5. After the above, run `dependencyClosure` over the final selected id set and add every pulled-in dependency to `selected` with `sectionReasons[depId] = { kind: "dependency" }` **only if** it doesn't already have a reason from steps 1-4 (a dependency that was independently selected keeps its own `"selected"` reason, not `"dependency"` — don't overwrite a more specific reason with a less specific one). Dependencies added this way are not subject to the budget check in step 2 — a selected section's required context always comes with it; this can make the true delivered size exceed `budgetChars` by a bounded amount (the size of one dependency chain), which is an accepted tradeoff, not a bug — document it in a comment.
  6. `evaluated` = union of every id that received either answer (relevance or contradiction), regardless of outcome.
- `decideFocusMode(evaluated, selected, catalog): FocusMode` — pure, no I/O: `selected` non-empty → `"select"`; `selected` empty and `evaluated` non-empty (Jev ran and found nothing above threshold) → `"compute_or_retrieve"` (recommends the caller show a minimal bounded view plus F0's `read_output`/`search_output` retrieval guidance, rather than either the full text or a guessed selection); `evaluated` empty (nothing was ever assessed — the exhaustive-bypass path, or total Jev failure) → `"full"`.
- `buildFallbackDecision(manifest): FocusDecision` — Jev unavailable. Per P4's fallback table, Focus's unavailable behavior is: *"Preserve an unfiltered bounded view with explicit coverage and recovery; still sanitize the exact delivered content."* This means the fallback decision is **always** `mode: "full"`, `status: "unavailable"`, `selected` an empty bitmap. **A caller must never read an empty `selected` bitmap under `mode: "full"` as "select nothing" — `mode` alone governs what to show; `selected` is only meaningful when `mode === "select"`.** Write this exact contract as a doc comment on `FocusDecision.selected` and assert it explicitly in a test (see §5) so a future reader of F2 doesn't wire `selected` through blindly.

## 3. ReflexEngine integration (packages/core/src/engine.ts)

Add a `focus` method mirroring `select`'s shape (batching loop, `this.request("focus", ...)` per batch, merge, partial-status, fallback-never-invents-content):

```ts
async focus(input: FocusInput): Promise<FocusDecision>
```

- If `isExhaustiveTask(input)` → return the exhaustive-bypass `FocusDecision` from §2 directly, no `this.request` call, no reflex journaled (mirrors `select`'s zero-eligible-candidates skip).
- Otherwise batch `input.manifest.entries` via `batchSections`, call `this.request("focus", <input.command.slice(0,80)>, state, questions)` per batch where `state = { task, command, intent, outcome, recentFindings, sections: batch.map(s => ({ id: s.id, text: s.text.slice(0, 2_000) })) }` — never send the whole manifest as one state object; only the current batch's sections, same discipline P7 used for candidates.
- Merge answers across batches exactly like `select`; `completedCount === 0` → `buildFallbackDecision(input.manifest)` with `status: "unavailable"`; `completedCount < batches.length` → `status: "partial"` using whatever answers did complete (unevaluated for the rest, never invented); `completedCount === batches.length` → `status: "ok"`.
- `recordDecision("focus", { action: decision.mode, reasons: [String(decision.batches), String(popcount(decision.selected)), input.manifest.catalogHash.slice(0,16)] }, subject, { judgmentId: <last batch's judgmentId> })`, same pattern as `select`.
- Add `private fallbackFocus(manifest: SectionManifest): FocusDecision { return { ...buildFallbackDecision(manifest), status: "unavailable", batches: 0 }; }` for symmetry with `fallbackSelect`/`fallbackGate`/etc., even though `buildFallbackDecision` does the real work — every reflex in this engine has a same-named private fallback method; don't break that pattern for the sake of one fewer function.

## 5. Tests

`packages/core/test/output-sections.test.ts`:
- blank-line-delimited text splits into the right number of sections, source order preserved, exact text preserved verbatim (no trimming beyond what the boundary itself consumes).
- a header line (`"FAIL auth.test.ts:"`) followed by an indented assertion block produces a child section whose `requires` includes the header's id; `dependencyClosure([childId])` returns `[headerId, childId]`.
- a single dense block with no blank lines (a 200-line stack trace) falls back to `LINE_WINDOW`-sized windows; the last window is shorter than 40 lines and does not throw or pad.
- Unicode round-trip: content containing emoji/CJK text has `endByte - startByte` for the section containing it strictly greater than that section's `text.length` (UTF-16 code units) — proves byte semantics, not string-length semantics.
- stdout and stderr split independently: calling `splitIntoSections` twice with the same textual content but different artifactId suffixes produces sections with different ids and no shared `requires` between the two manifests.

`packages/core/test/output-focus.test.ts`:
- exhaustive-task bypass fires on a keyword match (`"count how many tests failed"`) even for a large, structured output — asserts zero Jev calls via a spy-counted mock (use `mockSystemOne` with a call counter, same convention as other reflex tests).
- exhaustive-task bypass fires purely from `manifest.entries.length <= 1` even with no keyword.
- exhaustive-task bypass fires purely from total size `<= FOCUS_MIN_CHARS`.
- a section scoring above `relevanceNoul` is selected; its `requires` dependency (scored low or unevaluated) is pulled in with reason `"dependency"`, not `"excluded"`.
- a `contradicts_hypothesis` answer above threshold selects an otherwise-excluded section.
- budget enforcement: construct sections whose sizes force the loop to stop partway through the sorted-by-score order; assert the excluded tail is `"over_budget"`, not `"excluded"` — these must be distinguishable in `sectionReasons`.
- a missing answer for one candidate → `"unevaluated"`, distinguishable from a low score.
- all sections scored below threshold and no contradiction flips → `mode: "compute_or_retrieve"`, `selected` empty, `evaluated` non-empty.
- Jev unavailable (mock throws / `mockSystemOne` configured to report unavailable, same convention P4's tests use) → `mode: "full"`, `status: "unavailable"`, and a test that explicitly checks `selected` is *not* consulted by asserting the decision's own doc-comment contract via a helper (e.g. a small assertion function `assertFullModeIgnoresSelected(decision)` that intentionally does not inspect `popcount(decision.selected)` for correctness — the point is the test suite must not accidentally start relying on `selected` being empty as the "mechanism" for `full` mode).
- a batch failure partway through (mirroring P7's partial-batch test) leaves earlier batches' scores intact and reports `status: "partial"`.
- a single section whose own serialized question exceeds `FOCUS_BATCH_CHAR_BUDGET` still gets its own batch, never silently dropped.

`packages/core/test/engine.test.ts` (extend): `engine.focus` with a live `mockSystemOne` — reflex+decision journaled per batch; exhaustive bypass makes zero SystemOne calls (spy count).
