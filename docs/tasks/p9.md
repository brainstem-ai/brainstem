# Task P9: Faithful policy replay (evaluation tooling deferred)

Repo: brainstem (bun + TS). Baseline: journal v2 with stable IDs throughout (P2-P8), `packages/cli/src/replay.ts` (already resolves most decisions by `judgmentId`, partially built in an earlier phase). All tests green.

**Scope note.** The plan's P9 bundles two different things under one ID: faithful replay (offline, deterministic, no API calls — buildable and testable today) and evaluation tooling (live model-tier comparisons, cost/context benchmarking, an extended RTK baseline, held-out human-reviewed labeled sets). The second half requires live API spend and ground-truth data that does not exist in this repo. Building it responsibly means designing a report schema, running real tasks against real models, and getting review on what "acceptable outcome regression" means before any threshold is chosen — not something to charge through unsupervised. This unit is **replay only**. Section 4 below states exactly what evaluation work is deferred and why, so it isn't silently dropped from the plan.

## 1. A real correctness gap in the current replay

Read `packages/cli/src/replay.ts` and `packages/cli/test/replay.test.ts` before starting. The current implementation has a latent bug: when a `"decision"` event has no `judgmentId` (a static-floor verdict — `staticVerdict` present, never sent to Jev), it falls back to `lastAnswers.get(event.reflex)` — the answers from the **most recently seen** reflex of that type, which may be a completely unrelated judgment from an earlier turn. This is exactly the "last matching event" heuristic P2 introduced stable IDs to eliminate. It happens to not trigger in the current test suite only because no existing fixture has a successful judgment immediately preceding an unrelated static decision of the same reflex — construct that scenario and it silently fabricates a "replayed" verdict for a decision Jev was never involved in.

Fix: a decision is only replayable when it carries an explicit `judgmentId` that resolves to a recorded reflex event with real (non-null) answers. Remove `lastAnswers`/`lastSubjects` as an answer-resolution fallback entirely — keep `lastSubjects` (or equivalent) only for cosmetic subject display when a decision's own subject isn't separately recorded, never for resolving which answers apply.

## 2. Categorize every decision, don't silently drop the ones you can't replay

Today, `select` and `focus` decisions are invisible to replay — `DECIDERS` has no entry for them, so they fall through `if (!decide || !answers) continue;` without being counted anywhere. A user reading a replay report has no way to know whether their journal contained zero such decisions or several that were silently skipped.

`decideSelect`/`decideFocus` cannot be genuinely replayed with the current journal schema: they need the full capability catalog or section manifest (bitLength, catalogHash, index-to-id mapping) to reconstruct a `CapabilityBitmap`, and only the current batch's candidate descriptors are recorded in a reflex event's `state` — not the full catalog. Building a catalog/manifest-snapshot journal event to make this possible is real, scoped work of its own (a new journal event type, harness wiring to emit it once per catalog change, and bitmap round-trip tests) — it is a prerequisite for full select/focus replay fidelity, not a detail to improvise here. Defer it explicitly (§4).

Until that exists, make select/focus decisions **visible but explicitly unsupported** rather than invisible:

```ts
export type ReplayOutcome = "replayed" | "staticOnly" | "unsupported";

export interface ReplayReport {
  total: number;        // count of REPLAYED decisions only — same meaning existing tests already assume
  unchanged: number;
  changed: ReplayChange[];
  staticOnly: number;    // decisions with no judgmentId — static floor verdicts, not a Jev judgment
  unsupported: number;   // has a judgmentId, but no known decider (select/focus) or the reflex/answers can't be resolved
  unsupportedReasons: Record<string, number>;  // e.g. { "select: catalog not recorded": 3, "focus: manifest not recorded": 1, "missing reflex": 1 }
}
```

- `staticOnly`: `event.judgmentId === undefined`. Never attempt answer resolution for these at all.
- `unsupported`: `event.judgmentId !== undefined` but either (a) `event.reflex` is `"select"` or `"focus"` (no catalog/manifest recorded — tag reason accordingly), or (b) the judgmentId doesn't resolve to a reflex event with non-null answers (legacy/corrupt data — tag reason `"missing reflex"`).
- `replayed`/`total`/`unchanged`/`changed`: unchanged meaning from today, but now strictly gated on a resolved `judgmentId` — no fallback path.

## 3. CLI: make the offline/live distinction explicit, don't silently no-op

`packages/cli/src/main.ts`'s `runReplay` only supports offline policy replay today (correctly — it never calls Jev). The plan requires an explicit CLI mode for re-evaluation so a user can't mistake "nothing happened" for "it worked." Add `--mode policy|reevaluate` (default `policy`); `reevaluate` is not implemented in this unit — make the CLI say so and exit nonzero, rather than silently accepting and ignoring the flag:

```
brainstem replay <journal.ndjson> [--trust N] [--mode policy|reevaluate]
```

`--mode reevaluate` → `console.error("live re-evaluation is not implemented — replay only recomputes deterministic decisions from recorded scores. Re-run the task to get a fresh judgment."); process.exit(1);` before touching the journal at all.

Print the new report fields in `runReplay`'s output:

```
replay: <n> events, trust <t>
decisions replayed: <total>  unchanged: <unchanged>  changed: <changed.length>
static-only (no judgment, floor decided): <staticOnly>
unsupported: <unsupported>
  select: catalog not recorded: 3
  missing reflex: 1
```

Only print the `unsupported` breakdown lines when `unsupported > 0`.

## 4. Explicitly deferred (do not build these here)

State these plainly in the PR/commit description, don't silently drop them:

- **Catalog/manifest-snapshot journal event.** Prerequisite for genuine select/focus bitmap replay. Real, scoped work: a new event type, harness wiring to emit it once per catalog change (not every decision), and round-trip tests. Not started.
- **Live re-evaluation mode.** Explicitly guarded against (§3), not implemented — requires new API calls, spend limits, and a decision about which provider/model to re-ask with.
- **Evaluation scenario suite, RTK baseline extension, held-out labeled sets, cost/context/model-tier comparison, ablation harness.** All of the plan's "Evaluation" subsection. This needs a report schema design, live task runs against real models with bounded spend, and — for the held-out labeled set specifically — human-reviewed ground truth that does not exist in this repo yet. None of it can be responsibly built as a side effect of a replay-correctness fix.

## 5. Tests

`packages/cli/test/replay.test.ts` (extend, keep existing tests passing unmodified):

- **The bug this unit fixes:** a successful gate reflex+decision (auto, high confidence) immediately followed by a *different*, static-floor gate decision (no judgmentId, `staticVerdict: "deny"`) for an unrelated subject — assert the static decision is counted in `staticOnly`, never in `total`/`changed`/`unchanged`, and specifically that a stricter policy re-run does **not** report it as "changed" (which would prove the stale-answer fallback fired).

- A decision with a `judgmentId` that resolves to no reflex event at all (corrupt/truncated journal) → `unsupported` with reason `"missing reflex"`, not silently dropped and not crashing.
- All four existing tests in this file continue to pass with no modification — this is a correctness fix and a report-shape extension, not a semantics change to what "replayed" already meant.
