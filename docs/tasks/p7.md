## 1. packages/core/src/selection.ts (new)

```ts
export interface SelectableCapability {
  descriptor: CapabilityDescriptor; // from capabilities.ts
  index: number;                    // position in catalog.entries — stable for this catalog only
}

export interface SelectInput {
  task: string;
  recent: string[];                 // recent activity lines, same shape harness already builds for pulse/steer
  catalog: CapabilityCatalog;
  available: CapabilityBitmap;
  baseline: CapabilityBitmap;
  explicit: CapabilityBitmap;
  current: CapabilityBitmap;        // active set from the previous selection, for retention scoring
  discoveryQuery?: string;
}

export type SelectReason =
  | { kind: "added"; score: number }
  | { kind: "retained"; score: number }
  | { kind: "excluded"; score: number }
  | { kind: "unevaluated" }
  | { kind: "pinned" };

export interface SelectDecision {
  evaluated: CapabilityBitmap;
  recommended: CapabilityBitmap;
  scores: Record<string, number>;      // capability id -> raw noul score, evaluated ids only
  reasons: Record<string, SelectReason>;
  status: "ok" | "partial" | "unavailable";
  batches: number;                     // how many Jev requests this decision took
}
```

- `eligibleForSelection(catalog, available, baseline, explicit): SelectableCapability[]` — code, not Jev: a capability is eligible when it is available, not baseline, and not explicit. Baseline and explicit are never asked about; code always includes them (existing `computeActive` behavior — do not re-derive it here).
- `buildSelectQuestions(candidates: SelectableCapability[]): Record<string, Question>` — one independently scoped `noul` per candidate, id = `select__<capability-id-with-":" replaced by "_">` (colons are not safe as bare object-key/id fragments elsewhere in this codebase; follow the existing `select__` prefix so decoding is unambiguous — write `decodeSelectId`/`encodeSelectId` as the single pair of functions responsible for that mapping, and route every id through them instead of inlining the replace elsewhere). Instructions reference the candidate's `description` plus `useWhen`/`avoidWhen` verbatim: "Given `task` and `recent`, would the capability described here help perform the next step? id: `<id>`, description: `<description>`. Use when: `<useWhen.join('; ')>`. Avoid when: `<avoidWhen.join('; ')>`." Noul only — no confidence field, per P4's validation (a Noul answer is a bare probability; do not invent a second field).
- `decideSelect(catalog, candidates, answers, current, policy): { recommended: CapabilityBitmap; scores; reasons }` — pure function, mirrors `decideGate`/`decidePulse` style (no I/O, no engine state):
  - add threshold `policy.select.addNoul` (default `0.65`), retain threshold `policy.select.retainNoul` (default `0.45`).
  - a candidate scores >= add threshold → recommended, reason `added`.
  - a candidate that is currently active (bit set in `current`) and scores >= retain threshold (but below add) → recommended, reason `retained`.
  - anything else scored → not recommended, reason `excluded`.
  - a candidate present in `catalog` but absent from `answers` (missing response) → not recommended, reason `unevaluated`. Do not silently drop it from `reasons`; the caller must be able to tell "scored low" from "never assessed".
  - a candidate active in `current` that is not in the eligible set at all this round (e.g. became baseline/explicit) is simply not select's problem — it is handled by `computeActive`'s own seeding, not by this function. Do not add pass-through logic for it here.

## 2. Batching by size (packages/core/src/selection.ts)

- `SELECT_BATCH_CHAR_BUDGET = 6_000` (configurable via an optional param, not policy — this is a wire-size limit, not a decision threshold). Estimate a candidate's serialized size as `JSON.stringify(question).length` before batching; split candidates into ordered batches that each stay under the budget, preserving catalog order. A single candidate whose own serialized question exceeds the budget still gets its own one-candidate batch (never dropped silently).
- `SelectDecision.batches` records how many requests were actually issued (>= 1 when there is >= 1 eligible candidate, 0 when there are none — zero eligible candidates is not a Jev call at all, and must not journal a reflex event).
- Batches execute sequentially through the same `ReflexEngine.request` plumbing (see §3) so each batch gets its own judgment record and can fail independently: a broken batch 2 of 3 must not discard batch 1's valid answers. Merge partial results: `status` is `"ok"` only if every batch completed; `"partial"` if some completed and at least one did not; `"unavailable"` if none did. A `"partial"` or `"unavailable"` status still returns whatever `scores`/`reasons` were actually produced — never invent scores for the failed batches, and mark their candidates `unevaluated`.

## 3. ReflexEngine integration (packages/core/src/engine.ts)

Add a `select` method following the exact pattern of `pulse`/`steer` (call `this.request(...)` per batch, `recordDecision`, fallback on non-"completed" status):

```ts
async select(input: SelectInput): Promise<SelectDecision>
```

- Compute `eligibleForSelection` once. If empty, return `{ evaluated: createBitmap(catalog.catalogHash, catalog.entries.length), recommended: createBitmap(...), scores: {}, reasons: {}, status: "ok", batches: 0 }` without calling `this.request` — no reflex event, matching how gate skips Jev for `writes_outside_project`-style code-decidable cases.
- Otherwise batch per §2, call `this.request("select", <task-derived subject string, e.g. task.slice(0,80)>, state, questions)` per batch where `state` is `{ task: input.task, recent: input.recent, discoveryQuery: input.discoveryQuery, candidates: <batch's descriptors: id, description, useWhen, avoidWhen — never the whole catalog, never a positional array that could be confused with bitmap positions> }`.
- On a batch's `judgment.status !== "completed"`: mark that batch's candidates `unevaluated`, still process remaining batches, and use `fallbackSelect` for anything with zero completed batches:
  ```ts
  private fallbackSelect(catalog, current): SelectDecision {
    // Retain the last valid allowed set: recommended = current, filtered to what is
    // still in the catalog and available — nothing new is ever added on a fallback.
  }
  ```
  Per the P4 unavailable-behavior table: "Select | Retain the last valid allowed set; initially use baseline plus available explicit requirements and discovery" — baseline/explicit are already handled by `computeActive` unconditionally, so `fallbackSelect`'s only job is to preserve `current`'s optional (non-baseline/non-explicit) members that are still available, and mark everything else in the eligible set `unevaluated`. Never let a Jev outage *add* a capability that was not already active.
- `recordDecision("select", { action: <status>, reasons: [<batch count>, <recommended count>, <catalog hash prefix>] }, subject, { judgmentId: <last batch's judgmentId or undefined if zero batches ran> })`. Since `select` can span multiple judgments, also append one dedicated journal event per batch (reuse the existing `reflex`/`decision` events already emitted by `recordReflex`/`recordDecision` inside `this.request`/`recordDecision` — do not invent a new journal event type for this; the existing pair already captures per-batch state+questions+result and a linked decision).
- `evaluated` in the returned `SelectDecision` is the union of every catalog bit that received an actual answer across all batches (regardless of score) — this is what distinguishes "scored low" from "never assessed" per P6's mask design. A candidate whose batch failed is NOT in `evaluated`.

## 4. Retention, staleness, and refresh triggers (packages/cli/src/capabilities/select-policy.ts, new)

This is a thin CLI-layer driver, not core logic — it decides *when* to call `engine.select`, which core has no opinion about.

```ts
export interface SelectTrigger {
  reason: "initial" | "task_update" | "discovery" | "registry_change" | "new_failure_class" | "manual_refresh";
}

export class SelectDriver {
  constructor(deps: { registry: CapabilityRegistry; engine: ReflexEngine; minRefreshIntervalMs?: number });
  shouldRefresh(trigger: SelectTrigger, now: number): boolean;   // enforces minRefreshIntervalMs (default 5_000) except for "discovery" and "manual_refresh", which always run
  async refresh(input: { task: string; recent: string[]; discoveryQuery?: string }, trigger: SelectTrigger): Promise<SelectDecision>;
  currentDecision(): SelectDecision | undefined;                 // last successful-or-partial decision, for retention scoring and for Steer to read active ids from
}
```

- `refresh` calls `registry.snapshot()` for the catalog, builds `SelectInput` from the registry's current `available`/`baseline`/`explicit` bitmaps plus `currentDecision()?.recommended` (or an empty bitmap on first run) as `current`, calls `engine.select(input)`, stores the result, and returns it.
- Track a `catalogHash` alongside the stored decision; if `registry.snapshot().catalogHash` differs on the next `refresh`, drop the stored decision's `current` input (treat as first run) rather than remapping stale positional data across catalogs — P6's `computeActive`/bitmap code already forbids reusing bitmaps across catalog hashes (throws on mismatch), so this driver must not attempt to translate, only discard and reselect from empty.
- `registry.workingSet()` needs a way to receive an externally computed `recommended`/`evaluated` pair instead of always synthesizing empty ones. Extend `CapabilityRegistry.workingSet` with an optional `selected?: { evaluated: CapabilityBitmap; recommended: CapabilityBitmap }` parameter; when provided, use those bitmaps (after validating their `catalogHash` matches `registry.snapshot().catalogHash` — mismatch throws, same convention as the rest of this codebase) instead of the always-empty ones it creates today. Do not change the zero-arg call sites (harness's `activeCapabilityDescriptions` in Steer keeps working unmodified, still baseline+explicit only, until something actually passes a `SelectDriver`'s decision in).

## 6. Tests

`packages/core/test/selection.test.ts`:
- none eligible → zero-call `SelectDecision`, no reflex journaled.
- one eligible, scores above add threshold → recommended, reason `added`.
- one eligible, scores between retain and add thresholds but not currently active → excluded (retention only applies to already-active items).
- same mid-range score, but the candidate IS in `current` → retained.
- missing answer for one candidate in an otherwise-successful batch → that candidate `unevaluated`, others resolve normally, `evaluated` bitmap excludes it.
- oversized candidate set splits into multiple batches; a failure in batch 2 leaves batch 1's scores intact and status `"partial"`.
- a single candidate whose serialized question alone exceeds `SELECT_BATCH_CHAR_BUDGET` still gets evaluated (its own batch), not dropped.
- fallback (engine reports `unavailable`) never adds anything beyond what `current` already had.
- dependency: a capability recommended by Select whose `requires` are unmet is not this module's problem — assert `decideSelect`'s output bitmap does NOT itself resolve dependencies (that stays in `computeActive`); a unit test should show a recommended-but-dependency-broken id still appearing in `recommended` here, only to be dropped later by `computeActive`.
